# DS215H: дослідження application BIN V0.0.5

Аналіз виконано статично за файлом
[`APP_DS215H_V0.0.5_250905.bin`](firmware/APP_DS215H_V0.0.5_250905.bin),
SHA-256 `3a9b788147928093d4a6fbdf84df41b12a1587f742e8ff22d7940c60bffb7cae`.
Фізичний чип, його ID та вміст окремої Flash ще не прочитані. Адреси нижче —
адреси MCU; зміщення у BIN дорівнює адресі мінус `0x08007000`.

## Адреса образу та запуск

| Адреса | Зміщення в BIN | Що видно |
|---|---:|---|
| `0x08007000` | `0x00000` | Початок файла, таблиця векторів; перше слово `0x200361D0`. |
| `0x080072F0` | `0x002F0` | Reset handler, вказівник у таблиці `0x080072F1`. |
| `0x0802DB38` | `0x26B38` | Перевірка опційного байта, конфігурація SRAM. |
| `0x08024E6C` | `0x1DE6C` | Рання ініціалізація периферії, FPU та VTOR. |
| `0x0807F13F` | `0x7813F` | Останній байт application BIN; `0x0807F140` — кінець виключно. |

База `0x08007000` підтверджується тим, що reset vector указує саме на
початок логічного startup-коду за зміщенням `0x2F0`, а інші вектори й
абсолютні посилання узгоджуються з нею. Попереднє припущення про базу
`0x08000000` було помилковим. Область `0x08000000–0x08006FFF` не міститься
в цьому файлі; імовірно, там розташований bootloader, але його вміст ще не
досліджено. Від кінця BIN до `0x08080000` лишається `0xEC0` байтів; це не
підтверджує, що вони вільні або що фізична Flash має саме 512 KiB.

Reset handler спочатку ставить тимчасовий SP `0x20001000`, викликає
процедуру для конфігурації SRAM, потім завантажує SP зі слова за адресою
`0x08000000`. Ранній SystemInit записує `0x08000000` у VTOR. Тому не варто
припускати, що при запуску діє лише application vector table: механізм передачі
керування та переривань між bootloader і application ще треба відновити.

## MCU та попередня нумерація ніжок

У `0x0802DB38` код читає молодший байт `0x1FFFF810`, порівнює з `0xFE`, а
за іншого значення викликає послідовність налаштування; у `0x08030214` є
запис `0xFE` у цей option byte. Це відповідає EOPB0 для **AT32F403A/AT32F407**:
значення `0xFE` вибирає конфігурацію SRAM 224 KiB. Чи відбувався такий запис
на конкретному екземплярі, у статичному BIN невідомо. Слово SP у заголовку
`0x200361D0` потрапляє в SRAM `0x20000000–0x20037FFF` для конфігурації
224 KiB. GPIO, SPI2 і FLASH-регістри також збігаються з картою Artery.

Кандидат — **сімейство AT32F403A/AT32F407, Cortex-M4F**; саме це сімейство
поки не є остаточною ідентифікацією. Офіційні схеми LQFP100 в даташитах
AT32F403A та AT32F407 мають однакові позначення для перелічених нижче ніжок,
тому ці збіги не розрізняють F403A і F407. Обсяг вбудованої Flash конкретного
екземпляра також невідомий. Потрібні ID MCU через SWD або чітке маркування.
Значення `AT32` у USB-дескрипторі — лише додаткова
підказка, оскільки його може задати розробник.

Виправлення щодо попереднього кандидата STM32H7A3: у функції за
`0x0803BF3C` значення CPUID `0x410FC270` та `0x410FC271` порівнюються з
апаратним регістром; при збігу код зупиняється в нескінченному циклі. Це
узгоджується з `configASSERT` у FreeRTOS порту ARM_CM4F, який відхиляє
Cortex-M7 r0p0/r0p1, і не є доказом наявності M7. Конфігурація SRAM і
периферійна карта додатково суперечать H7A3.

Нижче **умовне** зіставлення для AT32F403A LQFP100, якщо перший вивід біля
маленької позначки в нижньому лівому куті фото. Колонка «на фото» — попередня
нумерація користувача; поворот на 50 позицій ще треба підтвердити на платі.

| На фото | AT32F403A pin | Сигнал | Підстава |
|---:|---:|---|---|
| 1 | 51 | PB12, SPI NOR CS | Драйвер опускає PB12 на час команд SPI. |
| 2 | 52 | PB13, SPI2 SCK | Pinout та ініціалізація PB13 для SPI2; трасу перевірити. |
| 3 | 53 | PB14, SPI2 MISO | Pinout та ініціалізація PB14 для SPI2; трасу перевірити. |
| 4 | 54 | PB15, SPI2 MOSI | Pinout та ініціалізація PB15 для SPI2; трасу перевірити. |
| 17 | 67 | PA8 | На фото веде до `TC4056A CHRG`; код читає PA8 і вибирає картинки `57.jpg`/`58.jpg`. |
| 18 | 68 | PA9 | На фото веде до `TC4056A STDBY`; призначення саме цієї лінії в коді не доведено. |
| 20 | 70 | PA11, можливий USB D− | Лише функція за datasheet; фізичну доріжку не підтверджено. |
| 21 | 71 | PA12, можливий USB D+ | Лише функція за datasheet; фізичну доріжку не підтверджено. |
| 62 | 12 | HEXT_IN | Очікуваний другий контакт кварцу; доріжка не підтверджена. |
| 63 | 13 | HEXT_OUT | За відео йде до компонента 8.000 MHz. |
| 79 | 29 | PA4/DAC1 | Код налаштовує PA4 і DAC1; призначення вузла не встановлено. |
| 80 | 30 | PA5/DAC2 | Код налаштовує PA5 і вмикає DAC2; на відео доріжка ймовірно йде до виходу генератора. |

Зокрема `0x0802FB7C–0x0802FBD8` ініціалізує PB12–PB15 та SPI2, а
`0x08026D86–0x08026DA2` налаштовує PA5 і `0x08026F26–0x08026F30` вмикає
DAC channel 2. Функція біля `0x0801AF28` читає `GPIOA_IDT` bit 8 і вибирає
шлях до однієї з двох системних картинок. Призначення PA8 як CHRG випливає
зі спостереження доріжки користувачем, а не з назви у BIN.

## Зовнішня SPI NOR і файли

Драйвер SPI NOR має такі функції:

| Адреса MCU | Функція, встановлена за кодом |
|---|---|
| `0x0802FAC4` | `0x90`: зчитування двобайтового manufacturer/device ID. |
| `0x0802FA78` | `0x20`: стирання сектора з 24-бітною адресою. |
| `0x0802FC24` | `0x03`: читання даних з 24-бітної адреси. |
| `0x0802FCF8` | `0x05`: опитування статусу, очікування звільнення. |
| `0x0802FF20` | `0x06`: дозвіл запису. |
| `0x0802FF48` | `0x02`: програмування сторінки з 24-бітною адресою. |

`0x0802FAC4` накопичує два прочитані ID-байти у локальну змінну, але перед
поверненням встановлює `r0 = 0x40010C00` для підняття CS і значення ID не
відновлює у `r0`. У виклику з `0x0802FC1A` результат теж не аналізується.
Тому твердження, що прошивка *використовує* ID для визначення місткості,
підстав не має. Це також пояснює, чому одного пошуку за JEDEC ID недостатньо.

Файлова система розрізняє logical drives `2:` та `3:`. У
`0x0802A738–0x0802A77C` і в шляху читання файлу `0x0802EA0E–0x0802EA68`
адреса для `3:` обчислюється як `sector * 4096`, а для `2:` як
`0x200000 + sector * 4096`, після чого викликається SPI NOR read `0x0802FC24`.

| Логічна область | Адреси в SPI NOR | Призначення за шляхами |
|---|---|---|
| `3:` | від `0x000000`, розмір USB-представлення 2 MiB | `3:/System file/*.jpg`, зокрема `3:/System file/999.bin`. |
| `2:` | від `0x200000`, розмір USB-представлення 14 MiB | `2:/LOGO/LOGODS215H.jpg`, `2:/Screenshot file/*.bmp`, `2:/Screenshot simple file/*.bin`. |

У USB SCSI-коді `0x0802A210–0x0802A246`, `0x0802A5B4–0x0802A5CA` задано
`0x200` або `0xE00` блоків по `0x1000` байтів. У другому режимі звичайні USB
read/write додають `0x200000` до адреси перед викликом SPI-драйвера
(`0x0802A35A–0x0802A3D2`). Межі двох представлених областей разом досягають
`0x1000000`, тобто firmware розраховує на **16 MiB доступного адресного
простору**. Це підтверджує попередню оцінку 128 Mbit класу, але фізична
місткість могла бути більшою. Це не встановлює, як окремий том IAP із
попередніх експериментів зіставлений із цими областями.

Зв’язок системних JPG з фізичним драйвером можна простежити так:

1. `0x080109A8` передає шлях `3:/System file/70.jpg` у `0x08033B0C`.
2. `0x08033B36` відкриває файл через `0x0802E474`; декодер за `0x08033BC2`
   отримує callback читання `0x08031090`.
3. Callback викликає файлове читання `0x0802E878`, яке для диска `3:` врешті
   викликає SPI NOR read `0x0802FC24`.

Таким чином, **ці системні зображення завантажуються із зовнішньої SPI NOR**.
Текстові ресурси та інші дані присутні у самому BIN; це не означає, що всі
ресурси інтерфейсу лежать в одному місці. Рядок `FAT32` свідчить про підтримку
цього формату кодом, але тип кожного реального тому потребує читання boot sector.

### Службовий перемикач USB

Під час ініціалізації `0x0802F464–0x0802F4A8` прошивка пробує відкрити
`3:/System file/999.bin`. Якщо відкриття успішне, прапорець за адресою RAM
`0x2000191A` стає `0`; за будь-якої помилки — `1`. USB SCSI-код використовує
цей прапорець: `0` вибирає 14 MiB від зсуву `0x200000`, `1` — 2 MiB від нуля.
Отже, файл, імовірно, служить перемикачем користувацького та системного тому.
У USB-шляху присутній і запис, тому зміна або видалення файла може зробити
системні ресурси доступними для змін; перед експериментами потрібна резервна
копія, а фактичну поведінку ще слід перевірити на приладі.

## Генератор і DAC

У конфігурації біля `0x08026EEC–0x08026F00` канал DMA отримує кількість
передач `100`, адресу периферії `0x40007414` і адресу RAM `0x20001842`.
В офіційному AT32 SDK `0x40007414` — регістр даних DAC2 з вирівнюванням
12-бітного значення праворуч. У контролері DMA також вмикається циклічний
режим (`0x08026EE2–0x08026EE8`). Отже, прошивка відтворює циклічний буфер
зі 100 значень через DAC2. Конкретний вміст буфера, форма й точна частота
потребують додаткового трасування. Це добре узгоджується зі спостереженою
користувачем доріжкою від умовного PA5 до виходу генератора.

## Файли скриншотів

Код формує парні шляхи `2:/Screenshot file/%d.bmp` і
`2:/Screenshot simple file/%d.bin`. У процедурі запису близько `0x080360CC`
для `.bin` записується `0x39A` (922) байти з RAM, після чого наприкінці
додається 5 байтів. Код читання `0x08033EB0` виділяє буфер і запитує
`0x39F` (927) байтів, перевіряючи точну кількість. Це корисна зачіпка для
декодування форми сигналу/налаштувань, але поля та семантику цих байтів ще
не підтверджено реальним зразком. Не слід вважати доведеним, що всі файли
інших версій мають такий самий формат.

## Як повторити перевірки

Інструмент [`tools/firmware.py`](../tools/firmware.py) читає BIN і показує
адреси MCU та зміщення. Потрібен Python 3 і Capstone 5; локальний пакет можна
встановити `python -m pip install --target .tools/python capstone==5.0.9`.
Приклади:

```text
python tools/firmware.py summary
python tools/firmware.py disasm 0x0802A738 0x0802A782
python tools/firmware.py disasm 0x0802F464 0x0802F4AA
python tools/firmware.py disasm 0x0802FF20 0x0802FFC0
python tools/firmware.py calls 0x0802FC24
python tools/firmware.py strings "System file|Screenshot"
```

Пошук викликів сканує всі півслова та може знаходити фальшиві збіги в даних;
потрібно перевіряти межі інструкцій і контекст. Аналіз не змінює прошивку.
